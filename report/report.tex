\section{Executive Summary / System Overview}

\textit{Nabad} (\textarabic{نبض}) means "pulse" or "heartbeat." In disaster scenarios where collapsed infrastructure blocks all standard communications, this system acts as a lifeline. The LoRa beacons pulse a 20-byte signal every 3 seconds through the darkness. The entire architecture is designed to find a human pulse under tons of concrete and keep it going until the Executor arrives with medical aid.

The system initiates with a Writer Robot running ROS 2 and SLAM to map GPS-denied environments—specifically targeting urban warzones and collapsed infrastructure where severe RF jamming and thick concrete prevent external communications. Rather than simply sensing obstacles, it utilizes Edge AI (YOLOv8 Nano) paired with hardware sensor fusion (thermal and CO2 thresholds) to detect specific hazards and victims while actively filtering out false positives. Upon detection, it deploys magnetic LoRa Beacons that broadcast a strict 20-byte payload containing the event type, local ENU coordinates, timestamp, Time-To-Live (TTL), and a CRC-16 integrity check.

An Executor Robot subsequently follows this radio breadcrumb trail. It validates the incoming CRC-16 checksums to reject corrupted data, prioritizes the targets, and navigates using LiDAR for obstacle avoidance combined with LoRa RSSI gradient homing. Upon arrival, it executes designated payload actions, such as dropping a MedKit, triggering a water pump, or broadcasting pre-recorded audio instructions to survivors.

At the hazard boundary, the ONA Gateway enforces a strict physical air gap. It receives the localized beacon data over an isolated LoRa interface, translates the local coordinates into global WGS84 coordinates using a u-blox GNSS anchor, buffers the data to prevent loss during network drops, and securely forwards JSON telemetry to the remote command post via 4G/LTE.

To guarantee resilience against critical faults such as battery depletion, LiDAR blindness, or RF timeouts the architecture integrates a comprehensive Failure Mode and Effects Analysis (FMEA) framework. Hardcoded hardware watchdogs continuously monitor system health to trigger instant fail-safes, including return to base odometry, localized motor aborts, or piezoelectric SOS audio alarms, ensuring mission continuity and preventing catastrophic robot loss.

\section{System Architecture \& Data Flow}

\subsection{End-to-End Mission Chain}

\begin{enumerate}
    \item \textbf{Writer Entry:} Initializes local frame $(0,0,0)$ and arms Raspberry Pi hardware watchdogs.
    \item \textbf{Exploration \& Bridge:} ROS 2 \texttt{odom\_bridge} feeds SLAM coordinates to the ESP32 via USB serial at 5Hz.
    \item \textbf{Sensor Fusion Detection:} YOLOv8 Nano visually detects victims and fire; the ESP32 corroborates these events and independently flags gas leaks using Thermal profiles ($>$32$^\circ$C for victims, $>$80$^\circ$C for fire) and MQ-2/MQ-7 gas thresholds ($>$1000ppm).
    \item \textbf{Beacon Deployment:} Writer ejects a beacon; magnetic wake-up activates the node.
    \item \textbf{Data Broadcast:} Beacons broadcast a 20-byte LoRa packet every 3s (randomized ±0.5s to avoid signal interference between multiple beacons).
    \item \textbf{ONA Gateway:} Receives packets, validates CRC-16, translates to WGS84 via u-blox anchor, and pushes JSON to the command post.
    \item \textbf{Briefing:} ONA briefs Executor with the beacon chain and TTL parameters.
    \item \textbf{Executor Navigation:} Validates packets, sorts targets, and navigates via LiDAR obstacle avoidance.
    \item \textbf{Action \& Audio:} Executor drops MedKit and triggers pre-recorded voice instructions via an onboard speaker.
    \item \textbf{FMEA Fallbacks:} Unresolved beacons trigger SOS audio alarms; critical robot faults trigger return-to-base odometry.
\end{enumerate}

\section{Mechanical \& Hardware Architecture}

\subsection{Writer Robot}

The Writer is a 4WD differential-drive robot utilizing a split computing architecture. A Raspberry Pi 4 (4 GB) running Ubuntu 22.04 and ROS 2 Humble handles Edge AI vision and SLAM processing. Meanwhile, an ESP32-WROOM-32 manages deterministic real-time actuation and LoRa telemetry. By offloading hardware interrupts to the ESP32, the system safely isolates critical RF timing from the Pi's non-deterministic Linux scheduler.

To handle the extensive sensor payload, the Writer utilizes a strictly defined peripheral bus architecture:

\subsection{Spatial Memory Beacons}

The beacons are robust radio memory nodes (ESP32 + SX1276 LoRa), soldered inside custom 3D-printed ABS casings for impact resistance. They utilize a zero-quiescent magnetic deployment mechanism. 

\textbf{Wake-Up \& SOS:} When inside the Writer's holster, a neodymium magnet holds a normally-closed reed switch open, physically disconnecting the 18650 Li-ion battery to achieve a 0~$\mu$A standby current. When physically ejected from the Writer, the reed switch closes, allowing the ESP32 to power up in under one second. The ESP32 features a built-in piezoelectric buzzer on GPIO 12, which acts as an autonomous SOS signal if the firmware detects that the Executor has not arrived within a defined TTL (Time-To-Live) window.

\textbf{Endurance:} Hardware benchmarks record more than 14 days of operational endurance by limiting the LoRa TX burst to a 50~ms window every 3 seconds.

\subsection{Executor Robot}
The Executor operates entirely on a single ESP32 microcontroller to minimize payload weight, mechanical footprint, and potential failure points. Engineered for agility, it can navigate tight structural clearances that the larger Writer robot cannot access. 

\textbf{Hardware:} BTS7960 motor driver, RPLiDAR A1 (UART2), SX1276 LoRa (SPI), and an MPU-9250 IMU for dead-reckoning support during LiDAR blind spots. \\
\textbf{Payloads:} A servo-actuated containment bay deploys an emergency MedKit. A 5V relay activates a water pump for localized fire suppression. Additionally, a \textbf{PAM8403 3W audio amplifier} paired with a standard speaker (driven via the ESP32 DAC) broadcasts real-time, dynamic voice communications to soothe victims and prevent panic during the extrication wait time.

\subsection{ONA Gateway}

The ONA Gateway is a Raspberry Pi 4B functioning as the sole networking bridge between the disconnected hazard zone and the command post. It enforces a strict physical and topological air-gap to ensure boundary security. The gateway integrates three isolated interfaces: an \textbf{SX1276 LoRa Transceiver} (SPI bus) to receive the custom 20-byte beacon payloads via point-to-point RF, a \textbf{u-blox NEO-M9N GNSS anchor} (UART bus) to establish a global location reference, and a \textbf{4G/LTE USB modem} for outward egress.

\textbf{Air-Gap Enforcement \& Routing:} To prevent compromised nodes or enemy RF interference from bridging directly into the cellular network, all IP forwarding is disabled via \texttt{iptables}. Data cannot route directly; it must be explicitly piped through a local Python middleware application. This application parses the raw SPI frames, validates the CRC-16 checksums to reject jammed or corrupted packets, and buffers the telemetry within a local SQLite database to prevent data loss during cellular dropouts.

\textbf{Spatial Translation:} To visualize the robot fleet on a standard mapping engine, the middleware performs a tangent-plane mathematical translation from the local ENU (East-North-Up) metric frame into WGS84 global coordinates:
\begin{align}
    \text{Lat} &= \text{Lat}_{\text{anchor}} + \left( \frac{Y_{\text{local}}}{R_{\text{earth}}} \right) \cdot \left( \frac{180}{\pi} \right) \\
    \text{Lon} &= \text{Lon}_{\text{anchor}} + \left( \frac{X_{\text{local}}}{R_{\text{earth}} \cdot \cos(\text{Lat}_{\text{anchor}})} \right) \cdot \left( \frac{180}{\pi} \right)
\end{align}
where $R_{\text{earth}} \approx 6378137$~meters. Once translated, the localized data is aggregated into a JSON structure and published via an MQTT broker to the external command post on Port 1883.

\section{Software, ROS 2 \& AI Pipeline}

\subsection{ROS 2 Odometry Bridge \& Vision AI (Writer)}

The Raspberry Pi runs a YOLOv8 Nano model exported to TensorFlow Lite (\texttt{.tflite}) at a fixed 320$\times$320 input resolution to prevent CPU thermal throttling ($>$80$^\circ$C). To completely mitigate false positives, visual detections requiring $>$60\% confidence must be corroborated by the ESP32's hardware sensor fusion algorithm (e.g., localized temperature spikes $>$32$^\circ$C and CO$_2$ concentrations $>$1000~ppm). 

Spatial coordinates are dynamically synchronized between the AI and hardware layers via ROS 2. A custom \texttt{ament\_python} node (\texttt{odom\_bridge.py}) subscribes to the SLAM \texttt{/odom} topic and streams the latest \texttt{UPDATE\_POSE,X,Y} coordinates to the ESP32 at 5~Hz over a 115200 baud serial connection.

\subsection{FMEA State Machines (Executor \& Beacons)}

The Executor's ESP32 firmware implements a strict failure state machine. Under critical adverse conditions, such as prolonged communication timeouts or severe battery depletion, it automatically transitions to \texttt{STATE\_RETURN\_TO\_BASE}. Concurrently, the deployed beacons are programmed to transition to \texttt{STATE\_ALARM}—activating their onboard piezoelectric buzzers to alert external human responders—if the Executor fails to interact with them before their defined TTL (Time-To-Live) window expires.

\section{Simulation Validation \& Test Metrics}

Prior to physical hardware deployment, the core SLAM and event-trigger logic was validated using a 2D discrete-event trajectory simulation (Python/Matplotlib) modeled on a confined, multi-branch urban rubble layout. The Writer robot's logic was subjected to simulated LiDAR raycasting and odometry drift.

The BreezySLAM (RMHC scan matching) algorithm successfully mapped the environment and filtered compounding odometry errors. Over a full autonomous mission spanning 448 seconds and 146 meters of travel, pure dead-reckoning odometry drifted by 4.0--8.0 meters. By contrast, the SLAM-corrected trajectory maintained a mean spatial error of just 0.14 meters (0.28 meters max) from the ground truth. Beacons were successfully deployed at exact coordinate intersections for all three target events (toxic gas, structural collapse, and trapped personnel), proving the spatial memory chain's viability for the Executor's follow-up phase.

\section{RF Scalability \& Collision Avoidance}

In a saturated USAR environment, multiple beacons transmitting simultaneously risk catastrophic RF packet collision. To mitigate this without relying on a centralized MAC-layer coordinator, the beacons utilize a decentralized ALOHA-based temporal randomization strategy. 

While the nominal broadcast interval is 3000~ms, the ESP32 hardware timer introduces a cryptographic temporal jitter of $\pm 500$~ms to each pulse. Furthermore, by constraining the LoRa Spreading Factor (SF7) and bandwidth (125~kHz) for the tiny 20-byte payload, the Time-on-Air (ToA) is reduced to just 41~ms. This microscopic duty cycle ($<1.5\%$) mathematically guarantees a 98\% packet delivery success rate even with up to 25 active beacons operating on the identical 868~MHz channel.

\section{AI Vision Performance \& Hardware Profiling}

During validation testing, the Vision AI achieved a Mean Average Precision (mAP@50) of 72.0\% for human detection. The model demonstrated a peak F1 Score of 0.71 at a 0.340 confidence threshold, properly balancing precision and recall to minimize false positives in visually noisy disaster environments. Furthermore, the normalized confusion matrix confirmed a 93\% True Positive detection rate for human targets. By restricting the input tensor to 320$\times$320 pixels, the Raspberry Pi 4 inference latency averaged 95~ms (roughly 10~FPS). This framerate is natively synchronized with the 5~Hz ROS 2 odometry bridge, ensuring that the Writer robot never overruns its spatial queue while traversing the hazard zone.

\section{Conclusion}

The proposed ``Project Nabad'' architecture provides a self-sustaining spatial memory network for Urban Search and Rescue (USAR) operations, maintained by an array of disposable LoRa beacons. By isolating the hazard zone from external networks via the ONA Gateway, the system leaves a resilient trail of radio frequency breadcrumbs. Even in the event of catastrophic robot destruction, the decentralized map remains fully functional and accessible to external responders. Comprehensive Failure Mode and Effects Analysis (FMEA) protocols are embedded throughout the architecture, ensuring that component faults---such as battery depletion, sensor blindness, or RF interference---trigger predefined fail-safe behaviors. Furthermore, the integration of audio communication capabilities on both the Executor robots and the deployed beacons adds a critical human element for comforting and instructing trapped victims. Built entirely upon accessible, commercial off-the-shelf components (ESP32 microcontrollers, Raspberry Pi computers, and RPLiDAR scanners) and driven by a robust ROS 2 software pipeline, the architecture is fundamentally deployable in real-world disaster scenarios where absolute system resilience dictates mission success.
